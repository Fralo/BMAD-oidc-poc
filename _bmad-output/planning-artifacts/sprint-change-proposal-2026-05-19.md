# Sprint Change Proposal — Split SPA out of BFF image

## 1. Issue Summary

### Trigger

Stakeholder direction (2026-05-19): treat the SPA and the BFF as two independent applications. The SPA must live in its own container with its own runtime, and the same-origin security model — the load-bearing property the project exists to demonstrate — must be preserved without conceding security or operator simplicity.

### Problem statement

The current architecture (decisions F3 + I6) bakes the compiled Angular `dist/` into the BFF image via a multi-stage Dockerfile and serves it from FastAPI's `StaticFiles` mount. This was an acceptable shortcut while Epic 1–5 focused on the OAuth surface, but it has three persistent costs:

1. **Conceptual conflation** — the FastAPI service has two unrelated jobs (serve Angular HTML; expose the BFF API). The `_spa_fallback` / `_json_404_fallback` machinery (Story 1.14 AC4) is a workaround for that conflation, not a feature.
2. **Build coupling** — every SPA change forces a rebuild of the BFF image; the Node toolchain ships into the Python image's build context unnecessarily. Story 1.14's repo-root build context exists to bridge this seam.
3. **No SSR option** — `architecture.md:289` locks `--ssr=false` because the BFF can only static-serve. The project cannot demonstrate Angular SSR even when stakeholders want it, because the serving model precludes it.

### Evidence

- `architecture.md` §F3 (lines 436–439): "BFF mounts `spa/dist/spa/browser` at `/`. Single origin everywhere".
- `architecture.md` §I6 (line 509): "Production-mode: BFF container is built via multi-stage Dockerfile that compiles the SPA in a Node stage and copies `dist/` into the BFF image".
- `services/bff/Dockerfile` Stage 0 (Node SPA builder) — currently part of the BFF image build.
- `services/bff/src/bff/main.py` — `_register_spa`, `_SPA_DIR`, `_json_404_fallback`, the `StaticFiles(.../assets)` mount, and the `FileResponse(.../index.html)` catch-all all exist to compensate for the conflation.
- `compose/app.yml:30–32` — BFF build context set to repo root specifically to reach `spa/` (Story 1.14's D4 resolution).
- Story 1.14 history (`_bmad-output/implementation-artifacts/1-14-...md`) is the codified rationale and is what this proposal supersedes.

### Stakeholder direction (2026-05-19)

- **Two-app separation:** SPA is its own service with its own runtime; BFF is API-only.
- **SSR on:** the SPA service runs Angular SSR (Node), generated by `ng add @angular/ssr`. The SSR Node process IS the edge and serves the browser everything (HTML and proxied API).
- **No extra proxy layer:** no Caddy / nginx / Traefik. The Express server built by `@angular/ssr` mounts `http-proxy-middleware` for `/auth/*`, `/api/*`, `/v1/*` and reverse-proxies to `http://bff:8000` over compose DNS.
- **New host port:** the SPA edge takes a fresh host port (e.g. `:4000`); the BFF loses its host port. Same-origin from the browser's perspective.
- **Containerized-only dev workflow:** the same SSR container is used in both modes; `ng serve --ssr` runs inside the container with proxy middleware wired in. No host Node toolchain needed.

### 2.2 PRD impact

No FR / NFR is invalidated. The two PRD properties that materially constrain the split are both **preserved by design**:

- **NFR1 (token isolation)** — unaffected. Tokens stay in the BFF; the SPA edge never sees them.
- **NFR10 (`docker-compose up` brings up the full topology)** — unaffected. The SPA edge becomes one more compose service.

One PRD elaboration is **clarified** rather than changed:

- **PRD §6 (system composition):** "SPA — Holds no tokens. Authenticates to the BFF via an HttpOnly session cookie. Communicates only with the BFF." This remains literally true — the browser still talks only to one origin (the SPA edge), which forwards `/auth/*`, `/api/*`, `/v1/*` to the BFF. The SPA's *browser-side* code still only knows about same-origin URLs.

The PRD's **CSP / cookie / CSRF** clauses are unchanged at the protocol level; only the **source of the CSP response header** moves (see 2.3).

## 3. Recommended Approach

**Option 1 — Direct Adjustment (selected).** A new mini-epic (Epic 6) with four backlog stories, executed in sequence, against the live `main` branch. No rollback, no MVP rescope.

### Rationale

- **Effort:** Medium. Four stories of similar size to Epic 1's later stories. SSR scaffolding + Express proxy + cookie forwarding + Dockerfile rewrite + compose surgery + Keycloak realm port + e2e config update + doc sweep. ~3–5 working days of focused execution.
- **Risk:** Low-medium. The OAuth/CSRF/JWT contracts the project demonstrates are byte-identical on both sides of the split; only the static-serve + redirect-host change. The biggest unknown is Angular 21's dev SSR integration, captured as a Story 6.1 close-gate.
- **Reversibility:** High. Story 6.3 is the only one that deletes production code; if Epic 6 is abandoned mid-flight, reverting that story's diff restores Story 1.14's surface.
- **Stakeholder alignment:** Directly implements the four stakeholder decisions captured in §1 (two-app split, Angular SSR, no extra proxy, new port, containerized dev).

### Alternatives considered (and rejected)

- **Option 2 — Rollback Story 1.14 then re-do.** No benefit. Story 1.14's deletion is mechanical and atomic in Story 6.3; rolling back first adds churn without clarification.
- **Option 3 — PRD MVP rescope.** No MVP change is required. The split is an architectural refinement, not a scope change.
- **Hybrid — single architecture-amendment story + single implementation story.** Considered. Rejected because the implementation has three loosely-coupled concerns (SSR scaffold; new container + realm + compose; BFF cleanup) and a final verification pass, each of which benefits from its own review surface.

## 4. Detailed Change Proposals

### Story 6.1 — Angular SSR scaffold, proxy middleware, cookie forwarding

**Goal:** The SPA project becomes an Angular SSR project. `ng add @angular/ssr` is applied; `server.ts` is customized with `http-proxy-middleware` for `/auth /api /v1` and a Node-only `REQUEST`-token cookie-forwarding interceptor. The `SSR_API_TARGET` token (per stakeholder's pasted snippet) is wired up and provided server-side from `process.env.BFF_INTERNAL_URL`.

**Touches:** `spa/angular.json`, `spa/package.json`, `spa/src/app/app.config.ts`, `spa/src/app/app.config.server.ts`, `spa/src/server.ts`, `spa/src/app/shared/http/ssr-api-url.interceptor.ts` (NEW), `spa/src/app/shared/http/ssr-cookie-forward.interceptor.ts` (NEW), `spa/src/app/auth/auth-guard.ts` (PLATFORM_ID short-circuit if needed), `spa/proxy.conf.json` (DELETE).

**Acceptance criteria sketch:**
- AC1 — `npm run build` produces both `dist/spa/browser` and `dist/spa/server`.
- AC2 — Running `node dist/spa/server/server.mjs` locally with `BFF_INTERNAL_URL=http://localhost:8000` serves `/` as SSR-rendered HTML and forwards `/api/me` to the BFF.
- AC3 — Dev mode: `ng serve` inside a container with SSR enabled exercises both the Angular dev pipeline AND the Express proxy middleware. If Angular 21's `@angular/build:dev-server` does not support custom middleware natively, fall back to `ng build --watch` + `node-with-restart` (documented in Dev Notes).
- AC4 — SSR-time `/api/me` calls carry the incoming browser's `bff_session` + `csrf_token` cookies into the BFF request via the cookie-forward interceptor.
- AC5 — `TransferState`-deduplicated bootstrap `/api/me` (no double-fire across SSR → hydration).
- AC6 — `SSR_API_TARGET` interceptor matches stakeholder's pasted pattern: `optional: true`, rewrites only `/api/*` (and `/auth/*` `/v1/*` per project paths) when token is present, no-op in the browser.
- AC7 — Unit tests for both interceptors with a synthetic `REQUEST` token; SPA Vitest suite stays green; coverage of new code ≥80%.

### Story 6.2 — SPA Dockerfile, compose service, Keycloak realm port

**Goal:** A new `spa` compose service exists, built from `spa/Dockerfile` (Node multi-stage: deps → build → runtime). It takes `${SPA_HOST_PORT:-4000}` on the host. The BFF loses its host-port mapping. Keycloak's realm registers the new redirect URI.

**Touches:** `spa/Dockerfile` (NEW), `spa/.dockerignore` (NEW), `compose/app.yml` (BFF service edits + new `spa` service block), `keycloak/realm-bmad-books.json` (`redirectUris` + `post.logout.redirect.uris` + `webOrigins`), `.env.example` (new `SPA_HOST_PORT` doc).

**Acceptance criteria sketch:**
- AC1 — `docker compose build spa` produces an image with `EXPOSE 4000` and an `ENTRYPOINT` that runs the SSR server.
- AC2 — `docker compose up` brings up Keycloak + BFF + RS + SPA; `docker compose ps` shows all four healthy within 120s.
- AC3 — `curl http://localhost:4000/` returns the SSR-rendered SPA shell (`<app-root>` present, plus SSR-injected initial-state markers).
- AC4 — `curl http://localhost:4000/api/me` returns the BFF's 401 envelope (proxy works).
- AC5 — `curl http://localhost:8000/` is unreachable from the host (BFF has no published port).
- AC6 — After `docker compose down -v && docker compose up`, the Keycloak realm registers `http://localhost:4000/auth/callback` as the only redirect URI for the BFF client. OAuth happy path completes against `testuser/testpassword` end-to-end from the operator's browser at `http://localhost:4000`.
- AC7 — `SPA_HOST_PORT=4100 docker compose up` brings the SPA up on `:4100` and Keycloak's realm honors it (env-driven realm-JSON via the existing import substitution).
- AC8 — BFF healthcheck unchanged; SPA healthcheck via `GET /_health`.
