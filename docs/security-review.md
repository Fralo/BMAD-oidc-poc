## 1. Token storage and transport

**Where access, refresh, and id tokens live.** Server-side only. On every successful OIDC login the BFF persists the three tokens to a `sessions` SQLModel row in the BFF's SQLite database (`/data/bff.db`, mounted from the `bff_data` named Docker volume).

```python
# services/bff/src/bff/models/entities/session.py:20–39
class Session(SQLModel, table=True):
    __tablename__ = "sessions"

    id: str = Field(primary_key=True)
    sub: str = Field(max_length=255, index=True, nullable=False)
    # `repr=False` keeps cryptographic material out of __repr__ / debug logs.
    access_token: str = Field(nullable=False, repr=False)
    refresh_token: str = Field(nullable=False, repr=False)
    id_token: str = Field(nullable=False, repr=False)
    expires_at: datetime = Field(index=True, nullable=False)
    csrf_secret: str = Field(nullable=False, repr=False)
    ...
```

The `repr=False` flag on the four cryptographic columns (`access_token`, `refresh_token`, `id_token`, `csrf_secret`) keeps token material out of any `__repr__` / debug-log surface — a small but important second-line defense against accidental leakage through Python's default object stringification.

**Transport between SPA ↔ BFF.** A single opaque HttpOnly session cookie. The cookie value is the `Session.id` column — generated by `secrets.token_urlsafe(32)` in `services/bff/src/bff/services/session_service.py`, which is 256 bits of cryptographic entropy. No business data is encoded in the cookie value; the row is the source of truth. The cookie name is configurable via the `BFF_SESSION_COOKIE_NAME` environment variable (default `bmad_books_session_id`).

The session cookie is set at `/auth/callback` time after a successful token exchange and verified at every subsequent BFF request via the cookie-session dependency on `/v1/*` and `/api/*` routes:

```python
# services/bff/src/bff/api/auth.py:298–305 (session-cookie set at /auth/callback)
# services/bff/src/bff/api/auth.py:347–355 (session-cookie clear at /auth/logout)
redirect.set_cookie(
    key=cfg.bff_session_cookie_name,
    value=session_row.id,
    httponly=True,
    samesite="lax",
    secure=cfg.bff_session_cookie_secure,
    path="/",
)
```

**Transport between BFF ↔ Resource Server.** `Authorization: Bearer <access_token>` header set by the `ResourceServerClient` on every RS call (`services/bff/src/bff/services/resource_server_client.py`). On a `401 invalid_token` from the RS the client refreshes the access token at Keycloak's `/token` endpoint using the refresh token, then replays the original request **exactly once**:

```python
# services/bff/src/bff/services/resource_server_client.py:230–279 (_call_with_refresh)
# services/bff/src/bff/services/resource_server_client.py:359–410 (_refresh_access_token)
```

A second 401 after refresh is treated as a hard authentication failure: the session row is deleted, the session cookie is cleared, and the SPA's next request receives the `SESSION_EXPIRED` envelope, prompting a fresh login. There is no second refresh attempt — the contract is one refresh per in-flight request.

**Why this isolation matters.** The architectural constraint "Token isolation" — `_bmad-output/planning-artifacts/architecture.md:36` and PRD §8 — mandates that "access and refresh tokens must never be transmitted to, stored in, or accessible from the SPA or any browser-accessible storage." The browser holds zero credential material that XSS or a malicious extension could exfiltrate. The cost of a compromised browser session is bounded to "an attacker can use the browser for as long as the current session cookie is valid"; the refresh token — the long-lived credential — never reaches the browser.

## 2. Session cookie attributes

The session cookie carries the following attributes, set verbatim at `services/bff/src/bff/api/auth.py:298–305` (the session cookie at `/auth/callback`) and mirrored — with matching attributes per RFC 6265bis — at lines 347–355 (the session cookie cleared at `/auth/logout`):

| Attribute | Value | Authority |
|-----------|-------|-----------|
| `HttpOnly` | `True` | architecture A4 (line 350) — prevents JavaScript / XSS read |
| `Secure` | environment-controlled by `BFF_SESSION_COOKIE_SECURE` | architecture A4 — `True` in prod; `False` for the local baseline stack to allow `http://localhost` |
| `SameSite` | `Lax` | architecture A4 — `Strict` would block the Keycloak post-callback redirect from carrying the cookie |
| `Path` | `/` | architecture A4 — entire BFF origin |
| Value form | opaque 256-bit token (`secrets.token_urlsafe(32)`) | architecture A4 — "not a JWT"; the row is the source of truth |
| Name | configurable via `BFF_SESSION_COOKIE_NAME` (default `bmad_books_session_id`) | `.env.example` |
| Max-Age / Expires | not set — session cookie; lives for the browser process lifetime | row-level `expires_at` is the authoritative TTL |

**Rationale for `SameSite=Lax` (not `Strict`).** The OIDC login flow ends with a `302 Location: https://bff/.../auth/callback?code=...&state=...` from Keycloak. The browser must include the BFF's cookies on that redirect for the callback handler to identify the session being completed (the state-id cookie, in particular — see below). `SameSite=Strict` cookies are NOT sent on cross-site-initiated navigations even when they land back on the same site, so the callback would arrive without the state cookie and the handshake would fail. `Lax` permits top-level GET navigations from cross-site contexts to carry the cookie, which is the exact path the OIDC redirect needs. The trade-off — `Lax` cookies ARE sent on cross-site top-level navigations — is acceptable here because every state-changing request is independently protected by the CSRF middleware (see §3).

**The state-id cookie sidebar.** During the OIDC login round-trip (`/auth/login` → Keycloak `/authorize` → Keycloak login form → Keycloak `/auth/callback?...` → back to BFF) the BFF maintains a separate short-lived cookie used only to bind the callback to the original `/auth/login` request:

```python
# services/bff/src/bff/api/auth.py:158–166
response.set_cookie(
    key=BFF_AUTH_STATE_COOKIE_NAME,
    value=signed_state_id,
    max_age=_STATE_COOKIE_MAX_AGE,   # 300 seconds (5 minutes)
    httponly=True,
    samesite="lax",
    secure=cfg.bff_session_cookie_secure,
    path="/",
)
```

The value is a `URLSafeTimedSerializer`-signed reference to a transient `auth_states` SQLModel row that holds `state`, `nonce`, and `return_to`. *(A vestigial `code_verifier` column survives in the row schema after the PKCE removal on 2026-05-21 but is no longer read or written.)* The signer is keyed by `BFF_CLIENT_SECRET` and produces a tamper-evident token that the callback can verify with no server lookup — the row is then loaded by id and consumed (deleted) at callback time. `Max-Age=300` enforces a five-minute window inside which the user must complete the OAuth dance. After successful callback the state-id cookie is cleared with `max_age=0` (see `services/bff/src/bff/api/auth.py:288–296`) using attributes that match the original set (RFC 6265bis requirement when `Secure` is true).

**The CSRF cookie sidebar.** The CSRF cookie is deliberately NOT HttpOnly — the SPA's CSRF interceptor must be able to read it in order to echo it back as the `X-CSRF-Token` header on state-changing requests. This is the standard double-submit-cookie pattern; the cookie content is not a secret in itself (the value is HMAC-derived per-session) and the threat the CSRF cookie defends against is cross-site request forgery, not XSS-driven exfiltration:

```python
# services/bff/src/bff/api/auth.py:307–314
redirect.set_cookie(
    key=cfg.bff_csrf_cookie_name,
    value=session_row.csrf_secret,
    httponly=False,                          # intentional — SPA reads it
    samesite="lax",
    secure=cfg.bff_session_cookie_secure,
    path="/",
)
```

**Edge-proxy footnote (Epic 6 split).** Post-Epic 6 the browser does not connect to the BFF directly — it connects to the SPA SSR edge on `http://localhost:${SPA_HOST_PORT:-4000}` (the only browser-facing host port; the BFF has no host port and is internal-only on the compose network). The SPA edge holds no auth state and never reads or modifies the cookies — it is a transparent in-network relay for the cookie surface. ## 3. CSRF posture

The BFF defends every state-changing request with three layers, applied in order. Any single failure rejects with `403 csrf_invalid`.

**Layer 1 — Method exemption.** Safe methods (GET / HEAD / OPTIONS) bypass the middleware entirely. Per [`services/bff/src/bff/auth/csrf.py:32`](../services/bff/src/bff/auth/csrf.py):

```python
_SAFE_METHODS: Final[frozenset[str]] = frozenset({"GET", "HEAD", "OPTIONS"})
```

The middleware's `dispatch` short-circuits when `request.method.upper() in _SAFE_METHODS` (line 59) — a `GET /v1/books` request is not subject to CSRF enforcement at all. Read-only operations are not state-changing; CSRF protection is about preventing forged state mutations.

A second exemption covers the bearer-authenticated `POST /v1/test/reset` endpoint (Story 1.12) at lines 48–50. That route authenticates via a shared bearer token (`Authorization: Bearer <TEST_RESET_TOKEN>`) rather than the session cookie; the CSRF check is bypassed because the cookie + double-submit mechanism is not the trust boundary on that path. The bearer-only mounting is gated by `ENABLE_TEST_RESET=true` (off by default) so the exemption is dead in production builds.

**Layer 2 — Double-submit cookie + custom header (constant-time compare).** On state-changing requests the middleware reads the `X-CSRF-Token` request header and the configured CSRF cookie (`bmad_books_csrf_token` by default — `BFF_CSRF_COOKIE_NAME`), then compares them with `hmac.compare_digest`:

```python
# services/bff/src/bff/auth/csrf.py:73–99
cookie_value = request.cookies.get(settings.bff_csrf_cookie_name) or ""
header_value = request.headers.get("x-csrf-token") or ""

if not header_value:
    logger.warning("csrf_header_missing path=%s method=%s", ...)
    return self._reject()

if not cookie_value or not hmac.compare_digest(
    header_value.encode("utf-8"), cookie_value.encode("utf-8")
):
    logger.warning("csrf_token_mismatch path=%s method=%s", ...)
    return self._reject()
```

The cookie value is the per-session `csrf_secret` column (`services/bff/src/bff/models/entities/session.py:30`), populated at session creation by `secrets.token_urlsafe(32)` — 256 bits of entropy distinct from the session ID. Constant-time comparison (`hmac.compare_digest`) prevents the timing-side-channel attack where an attacker measures response latency to recover the secret byte-by-byte.

The SPA half of the double-submit pattern lives in [`spa/src/app/shared/http/csrf-interceptor.ts`](../spa/src/app/shared/http/csrf-interceptor.ts), which reads the (intentionally non-HttpOnly) cookie at every state-changing fetch and sets the `X-CSRF-Token` header. The interceptor matches on method (POST / PUT / PATCH / DELETE) and is pinned by [`spa/src/app/shared/http/csrf-interceptor.spec.ts`](../spa/src/app/shared/http/csrf-interceptor.spec.ts).

**Layer 3 — `Origin` / `Referer` check.** Defense in depth. The middleware parses the configured `BFF_BASE_URL` once per request and compares its `(scheme, hostname, port)` tuple to either the request's `Origin` header (preferred) or `Referer` header (fallback). Mismatch → `403 csrf_invalid`.

```python
# services/bff/src/bff/auth/csrf.py:101–135
expected = self._parse_origin(settings.bff_base_url)
origin = request.headers.get("origin")
referer = request.headers.get("referer")

if origin and origin != "null":
    observed_match = self._origin_matches(origin, expected)
elif referer:
    observed_match = self._origin_matches(referer, expected)
else:
    observed_match = False

if not observed_match:
    logger.warning("csrf_origin_mismatch path=%s origin=%s referer_host=%s", ...)
    return self._reject()
```

The `_origin_matches` helper (lines 159–173) explicitly rejects URLs that carry userinfo (`http://attacker@host/`) by checking `parts.username or parts.password` on the parsed `urlsplit` result — a downstream hostname-based comparison would otherwise drop the userinfo (via `urlsplit(...).hostname`) and let an attacker craft a same-origin-looking value. Path / query / fragment are not security-relevant; `Referer` headers legitimately carry the path and the tuple comparison ignores it.

**Failure envelope.** Every rejection emits the canonical envelope built by `services/bff/src/bff/core/errors.py`:

```json
{
  "errorCode": "csrf_invalid",
  "message": "CSRF token validation failed.",
  "detail": null
}
```

with HTTP status `403`. The error code is defined at `services/bff/src/bff/core/errors.py` (`ErrorCode.CSRF_INVALID`).

- [`services/bff/src/bff/auth/csrf.py`](../services/bff/src/bff/auth/csrf.py) — middleware (`CsrfMiddleware.dispatch`), exempt-method list (line 32), constant-time compare (line 91), Origin/Referer logic (lines 101–135).
- [`services/bff/src/bff/main.py`](../services/bff/src/bff/main.py) — middleware registration order.

The SPA edge's `http-proxy-middleware` mount is configured with `changeOrigin: true` ([`spa/src/server.ts`](../spa/src/server.ts) line 59), which rewrites the upstream HTTP `Host` header to `bff:8000` on the inside, but the browser's `Origin` header passes through unchanged. The BFF's `_origin_matches` helper compares the unchanged `Origin` value against `settings.bff_base_url` (now `localhost:${SPA_HOST_PORT:-4000}`) and the values match. The trust boundary is unchanged from the pre-Epic-6 posture: the BFF still anchors its CSRF check on the browser's reported `Origin` against the configured browser-facing base URL; only the URL value changed. See Story 6.2 changelog for the realm + base-URL flip; see §"Edge proxy" subsection in §6 for the proxy semantics.

## 4. JWT validation correctness

**Library.** PyJWT (`pyjwt[crypto]`) on both BFF and RS. The RS uses `jwt.decode` for access-token verification; the BFF uses the same library to verify Keycloak-issued id-tokens during the callback exchange. The library choice was deliberately not `python-jose` (effectively abandoned per architecture line 348) and not a hand-rolled JWS verifier.

**What the RS validates on every authenticated request.** Per [`services/resource-server/src/resource_server/auth/oidc_bearer.py:76–93`](../services/resource-server/src/resource_server/auth/oidc_bearer.py):

```python
def _validate_access_token(token: str) -> dict[str, Any]:
    try:
        jwks_client = _get_jwks_client(settings.oidc_jwks_url)
        signing_key = jwks_client.get_signing_key_from_jwt(token)
        decoded = jwt.decode(
            token,
            signing_key.key,
            algorithms=["RS256"],
            audience=settings.oidc_audience,
            issuer=settings.oidc_issuer_url,
            options={"require": ["iss", "aud", "exp", "sub"]},
        )
    except (jwt.InvalidTokenError, jwt.PyJWKClientError) as exc:
        logger.warning("JWT validation failed: %s", type(exc).__name__)
        raise AppException(ErrorCode.SESSION_EXPIRED) from exc
```

The validation performs, in this order:

1. **JWKS key retrieval by `kid`.** `PyJWKClient.get_signing_key_from_jwt(token)` reads the token header's `kid`, looks it up in the client's in-memory key cache, and re-fetches from the JWKS endpoint on cache miss. This handles Keycloak key rotation without any operator intervention.
2. **Algorithm pinning.** `algorithms=["RS256"]` rejects any token signed with a different algorithm — including the `none` algorithm (CVE-2015-9235 class of attack) and any HS256 (symmetric-key) variant that would let an attacker forge tokens using the public key.
3. **Audience claim.** `audience=settings.oidc_audience` — set to `bmad-books-resource-server`. The Keycloak realm includes a hardcoded protocol mapper (`aud-resource-server`) that injects this value into every access token issued to the `bmad-books-bff` client.
4. **Issuer claim.** `issuer=settings.oidc_issuer_url` — pinned to the deployment's Keycloak realm URL.
5. **Expiry.** PyJWT verifies `exp` ≥ now (no `leeway` is configured today; see Known Gaps for the small-but-real clock-skew implication).
6. **Required-claims gate.** `options={"require": ["iss", "aud", "exp", "sub"]}` enforces that the token actually carries all four claims — a forged token that elided the audience claim would fail this check even before signature verification ran on a valid key. Note this is a **presence-only** check: PyJWT does not enforce non-empty values, so a token carrying an empty-string `sub` would pass this gate and surface downstream as `412 reading_speed_unset`. See Known Gap #5 (D67) for the empty-`sub` consequence.

Signature verification is performed by `jwt.decode` against the public key returned by the JWKS client. Tokens signed by any key not present in the JWKS endpoint are rejected with `jwt.InvalidTokenError`, which the handler maps to a `401 session_expired` envelope.

**Why JWKS, not a hardcoded public key.** Architecture line 40: "JWKS-based JWT validation. Public keys fetched and cached from the Authorization Server; no hardcoded keys." Key rotation at the IdP must not require redeploying the RS. The `_get_jwks_client` cache (line 52) holds a `PyJWKClient` per JWKS URL across the process lifetime; `cache_keys=True` keeps successfully-fetched keys until a `kid` miss triggers a single re-fetch. The **key-rotation half** of architecture line 415's "TTL 24h, key-rotation on `kid` miss (single re-fetch)" envelope is satisfied by this `kid`-miss re-fetch; the **24h time-based TTL half is not enforced** by PyJWKClient — a successfully-cached key with no intervening traffic is held indefinitely, not for 24h. See the implementation note at `oidc_bearer.py:42–48`. For the project's threat model this is acceptable because `kid` rotation is Keycloak's signal for "use new keys"; a key compromise would manifest as a `kid` change triggering re-fetch on the next traffic. Deployments that need a hard time-based bound would wrap `PyJWKClient` in a TTL-aware decorator or replace it with a manual cache.

**The BFF id-token parallel.** During `/auth/callback`, the BFF runs a structurally similar PyJWT validation on the id-token returned from `/token`:

```python
# services/bff/src/bff/api/auth.py:250–265 (callsite)
# services/bff/src/bff/auth/keycloak_cookie_session.py:204–246 (implementation)
claims = verify_id_token(
    id_token=id_token_jwt,
    jwks_url=cfg.oidc_jwks_url,
    expected_issuer=cfg.oidc_authorize_url_browser,   # D2/D8 caveat — browser-facing URL
    expected_audience=cfg.oidc_client_id,
    expected_nonce=row.nonce,
)
```

Two notable differences from the RS validation:

- **`expected_issuer` uses `oidc_authorize_url_browser`, not the back-channel issuer.** This is the resolution of defer D2 / D8 — Keycloak emits `iss=<KC_HOSTNAME>` in id_tokens, which equals the browser-facing URL (`http://localhost:8080`), not the in-cluster docker-DNS issuer (`http://keycloak:8080`). The verification uses the same value Keycloak signed.
- **`expected_nonce` is enforced.** OIDC nonce binding — the BFF generated this nonce in `/auth/login`, stored it in the `auth_states` row, and verifies it matches what came back in the id-token. This defends against id-token replay across login attempts.

## 5. Scope enforcement

**Enforcement happens at the Resource Server.** This is a load-bearing architectural rule (PRD §8 "Scope-enforced computation" / architecture line 42): the BFF forwards the user's bearer token unchanged; the BFF does not consult the scope claim; the RS — the resource owner — makes every authorization decision. A reviewer should be able to verify scope behavior by issuing a bearer to the RS directly and confirming the matrix below; no BFF involvement is required.

**The two domain scopes.**

| Scope | Granted to | Purpose |
|-------|------------|---------|
| `reading-speed:read` | `bmad-books-bff` client | Read the user's reading speed; compute estimates |
| `reading-speed:write` | `bmad-books-bff` client | Update the user's reading speed |

Both scopes are defined as **optional client scopes** in [`keycloak/realm-bmad-books.json`](../keycloak/realm-bmad-books.json) and requested at `/authorize` time by the BFF (`openid offline_access reading-speed:read reading-speed:write`). Keycloak grants them to the user's session because the user has the corresponding role mapping in the imported realm.

**The per-endpoint scope table.** Per [architecture §C3 (lines 382–388)](../_bmad-output/planning-artifacts/architecture.md):

| Method | Path | Required scope | Handler reference |
|--------|------|----------------|--------------------|
| `GET` | `/v1/reading-speed` | `reading-speed:read` | [`reading_speed.py:32`](../services/resource-server/src/resource_server/api/reading_speed.py) |
| `PUT` | `/v1/reading-speed` | `reading-speed:write` | [`reading_speed.py:42`](../services/resource-server/src/resource_server/api/reading_speed.py) |
| `POST` | `/v1/estimate` | `reading-speed:read` | [`estimate.py:42`](../services/resource-server/src/resource_server/api/estimate.py) |

The mechanism is a single FastAPI dependency factory:

```python
# services/resource-server/src/resource_server/auth/oidc_bearer.py:130–156
def require_scope(scope: str) -> Callable[..., Awaitable[Principal]]:
    # Fail fast at factory-call time on empty / whitespace-padded scope strings.
    if not scope or scope != scope.strip():
        msg = (
            f"require_scope() expects a non-empty, non-whitespace-padded scope; "
            f"got {scope!r}"
        )
        raise ValueError(msg)

    async def _dependency(
        principal: Annotated[Principal, Depends(get_authenticated_principal)],
    ) -> Principal:
        if scope not in principal.scopes:
            logger.warning(
                "Scope check failed: sub=%s requires %s",
                principal.subject,
                scope,
            )
            raise AppException(ErrorCode.FORBIDDEN_SCOPE)
        return principal

    return _dependency
```

Each endpoint declares its required scope via `Depends(require_scope("<scope>"))`. Missing scope → `403 forbidden_scope`. The factory is also a **module-load fail-fast guard**: an accidental typo like `require_scope(" reading-speed:read")` (note the leading space) would silently 403 every caller in production — instead, the `ValueError` at import time surfaces the typo as an `ImportError`-equivalent fail-fast. This is a deliberate trade-off explained in the code comment above the check (lines 131–136).

**Identity is sourced from the JWT — never from request body or path.** Per architecture line 388 ("All RS endpoints read user identity from the JWT `sub` claim — no path or body identifier accepted for user") and line 394 ("BFF never injects user identity into the body or path; the RS reads `sub` from the JWT only"). The RS's `_principal_from_claims` (lines 96–112) reads `sub` directly from the verified JWT; the BFF's compute-estimate path (`services/bff/src/bff/services/resource_server_client.py`) sends only `{"pages": <n>}` — never any user identifier. The threat-model writeup in §"Threat Model Summary" below pins the confused-deputy mitigation against this rule.

**A `bmad-books-bff-test` follow-up.** A defense-in-depth opportunity recorded in `deferred-work.md` as D440: today the e2e Playwright runner uses the same `BFF_CLIENT_SECRET` as the production confidential client. A future hardening pass would split these so that Playwright artifacts (traces, screenshots) captured during failed runs cannot leak a real client credential. Captured here under "Known Gaps".

**Implementing code paths:**
- [`services/resource-server/src/resource_server/auth/oidc_bearer.py`](../services/resource-server/src/resource_server/auth/oidc_bearer.py) — `require_scope` factory (line 130) + per-request `_dependency` closure.
- [`services/resource-server/src/resource_server/api/reading_speed.py`](../services/resource-server/src/resource_server/api/reading_speed.py) — `Depends(require_scope("reading-speed:read"))` at line 32; `Depends(require_scope("reading-speed:write"))` at line 42.

## 6. Standard SPA concerns

### Content-Security-Policy

The SPA SSR edge emits a single CSP response header on every SSR-rendered HTML response. The exact value, sourced verbatim from [`spa/src/server/csp.middleware.ts`](../spa/src/server/csp.middleware.ts) (Story 6.4 / architecture A8 amendment — CSP attachment moved from the BFF's Starlette middleware to the SPA edge's Express middleware; the value did not change, only the attaching service did):

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
```

Directive-by-directive:

| Directive | Value | Why |
|-----------|-------|-----|
| `default-src 'self'` | only resources from the SPA-edge origin | baseline lockdown |
| `script-src 'self'` | only scripts from the SPA-edge origin; no inline scripts | first-line XSS defense — even if an injection point exists in HTML, inline scripts won't execute |
| `style-src 'self' 'unsafe-inline'` | self + inline styles permitted | required because Tailwind v4 emits inline `<style>` content from the `@theme` block in `spa/src/styles.css` |
| `img-src 'self' data:` | self + data URLs | data URLs accommodate inline SVG / small placeholder icons used by Angular components |
| `connect-src 'self'` | only same-origin `fetch` / XHR / WebSocket | SPA only talks to the BFF via the SPA edge's same-origin proxy; no external API surface |
| `frame-ancestors 'none'` | no embedding under any origin | clickjacking defense; supersedes legacy `X-Frame-Options: DENY` |
| `base-uri 'self'` | `<base>` tag restricted | prevents an injected `<base href="https://attacker.example/">` from re-routing relative URLs |
| `form-action 'self'` | form submissions only to same origin | defends against form-action hijacking via injected `<form action="...">` |

**Attachment rule.** CSP is attached to every non-proxied response (SSR-rendered HTML and static browser assets) by the SPA edge's Express middleware, registered in [`spa/src/server.ts`](../spa/src/server.ts) at step 3 (after the proxy mount at step 2, before `express.static` at step 4 and the Angular SSR catch-all at step 5). The placement is load-bearing: BFF-proxied responses on `/auth /api /v1` (always JSON) short-circuit at the proxy mount and never reach the CSP middleware, so they correctly do NOT carry CSP. All remaining requests — SSR HTML rendered by the Angular handler AND static assets (JS bundles, CSS, fonts, images) served by `express.static` — pass through the CSP middleware first, so they DO carry CSP. Attaching CSP to static assets is harmless and matches the pre-Epic-6 BFF posture (`server.ts` lines 81–83). The middleware is unconditional (no request-`Accept` predicate, no response-`Content-Type` predicate) — middleware placement, not predicate logic, decides which surface gets the header. The historical request-`Accept`-header-driven attachment rule in the BFF middleware (D369) is moot post-6.4; D369 closes alongside the CSP source move. Probe 4 in [`docs/smoke-run.md`](smoke-run.md) (Epic-6 Run Record) is the live attestation: `curl -sSI http://localhost:4000/login` returns the byte string above, and `curl -sSI http://localhost:4000/api/me` (proxied to the BFF) does not.

The `style-src 'unsafe-inline'` carve-out is the one knowingly-relaxed directive. The architecture A8 decision (lines 350–354) accepts it as the cost of using Tailwind v4 without a build-time nonce-injector. Future hardening (D371) could remove the carve-out by computing a per-request nonce for the inlined Tailwind style block and threading it through the Angular bootstrap. This story does not undertake that work.

**Other security headers not currently attached.** A production-hardening pass would add `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security` (TLS-only deployments), `X-Frame-Options: DENY` (legacy fallback for `frame-ancestors`), `Permissions-Policy`, and the COOP/CORP/COEP triplet. Today only CSP is attached; the rest are documented as Known Gaps (D372).

### No tokens reachable from JavaScript

Restating §1's contract from the SPA perspective: the session cookie is `HttpOnly`; the only browser-readable cookie is the CSRF token (intentionally — it is not a secret); no access / refresh / id token ever reaches the browser. The architectural constraint "Token isolation" (architecture line 36) is the load-bearing rule and the §"Threat Model Summary" XSS entry below explains why this matters even when XSS is the assumed-compromised case.

### Edge proxy

**Edge-proxy security model.** Post-Epic 6 the SPA SSR Express server ([`spa/src/server.ts`](../spa/src/server.ts), Story 6.1) is a trusted in-network relay between the browser and the BFF. It runs on `http://localhost:${SPA_HOST_PORT:-4000}` (the only host-published port on the public-facing surface); the BFF has no host port and is reachable only at `http://bff:8000` on the compose network (Story 6.2 AC5; Probe 5 in the Epic-6 Run Record attests `http://localhost:8000/health` returns `connection_refused`).

**What the SPA edge does NOT carry.** No auth state, no token state, no session-cookie inspection, no CSRF state, no business logic. The Express middleware chain is, in registration order: `/_health` probe → `/auth /api /v1` proxy mount (`http-proxy-middleware` v3 with `changeOrigin: true`, `xfwd: true`) → CSP middleware (Story 6.4) → static-asset middleware → Angular SSR catch-all. The proxy mount injects `X-Forwarded-For`, `X-Forwarded-Host`, and `X-Forwarded-Proto` headers on every upstream request (`xfwd: true`); if a client sends a forged `X-Forwarded-For`, `http-proxy-middleware` appends rather than replaces — see D150 (trust-proxy not configured). No application-level header is read, modified, or removed by the SPA edge: `Cookie`, `Origin`, `X-CSRF-Token`, and `Authorization` (if any future call carries one) pass through byte-for-byte.

**Implications.** Compromise of the SPA-edge container compromises browser observability (an attacker with code execution in the container could log request bodies) but does NOT compromise tokens (still server-side at the BFF, untouched by the edge) or grant token-level access to the RS (the BFF still owns the bearer-attach step in [`services/bff/src/bff/services/resource_server_client.py`](../services/bff/src/bff/services/resource_server_client.py)). The SPA edge has the same trust profile as a TLS-terminating ingress in a production deployment — load-bearing for headers in transit, not for credentials at rest. CSRF posture is preserved exactly because the edge passes the browser's `Origin` header through unchanged (see §3 Edge-proxy footnote); session cookies are preserved exactly because the edge passes `Set-Cookie` / `Cookie` headers through unchanged (see §2 Edge-proxy footnote).

### Output escaping (XSS at the template layer)

Angular templates auto-escape interpolated values by default. The `{{ value }}` syntax HTML-escapes; the `[innerHTML]` binding (which would bypass escaping) is **not used anywhere in the SPA**. `DomSanitizer.bypassSecurityTrust*` family methods are not used. No `eval` / `Function` construction; no dynamic script injection.

A grep for risky patterns across the SPA codebase returns no hits at baseline `3e3612a`:

```bash
$ grep -r "bypassSecurityTrust\|innerHTML\|eval\(\|new Function(" spa/src/app/
# (no output — no matches)
```

## Accepted Risks

The architecture explicitly accepts the following risks for the educational reference. Each is named here with mitigation, the production-deployment alternative, and the architectural authority that ratified the trade-off. They are NOT bugs and they are NOT items the project failed to address — they are scope decisions the PRD §4 ("Production hardening beyond what the course's success criteria require") puts out of bounds.

### AR1 — Plaintext token storage in the BFF's SQLite `sessions` table

**Risk.** The BFF persists `access_token`, `refresh_token`, and `id_token` as plaintext `TEXT` columns in `services/bff/src/bff/models/entities/session.py` (`sessions` table, `/data/bff.db`). Any process with read access to the SQLite file can mint a successful RS call.

**Mitigation in this implementation.** The SQLite file lives in the `bff_data` named Docker volume, which is not bind-mounted to the host and not exposed on the network. The BFF process is the only consumer. The token columns are declared with `repr=False` so debug-log surfaces never spill them. The OIDC client secret used to refresh tokens (`BFF_CLIENT_SECRET`) is held only in env, never persisted.

**Production-deployment alternatives.**
1. **Application-level KEK encrypting the columns.** A key-encryption-key held in a secrets manager (AWS KMS, HashiCorp Vault, Azure Key Vault) encrypts the three token columns at row creation; the BFF process decrypts them only when forwarding to Keycloak / the RS. The SQLite file becomes safe to back up.
2. **Dedicated encrypted session store.** Move sessions to Redis or Postgres with envelope encryption + tighter access controls than SQLite-on-disk provides.
3. **Stateless JWE-encrypted session cookie.** Eliminate the at-rest concern by carrying the encrypted token bundle in the session cookie itself. Cost: larger cookies + a key-rotation story for the JWE key.

**Authority.** [`_bmad-output/planning-artifacts/architecture.md:1362–1368`](../_bmad-output/planning-artifacts/architecture.md) — "Operational Details" → "Token storage at rest." Explicitly out of scope per PRD §4.

### AR2 — *(retired 2026-05-21)*

The original AR2 documented an accepted risk: plaintext PKCE `code_verifier` storage in the `auth_states` table. PKCE was removed from the flow on 2026-05-21 (confidential-client `client_secret_basic` is now the trust basis; see Pattern Amendments in architecture.md). The `code_verifier` column survives in the schema as nullable dead storage but is no longer read or written — the at-rest plaintext-verifier risk no longer exists.

### AR3 — No idle-session timeout beyond the refresh-token-expiry chain

**Risk.** Today the session row expires when its `expires_at` (set from the id-token's `exp` claim at callback time) is reached. There is no separate idle-timeout tracking — a session that has been quiet for 8 hours but whose refresh token is still valid will silently come back to life on the next request.

**Mitigation in this implementation.** The refresh-token max lifespan is the practical bound — Keycloak's realm default is 30 days. When the session row is consulted on a request whose access token has expired, the refresh-and-replay path runs once; if Keycloak rejects the refresh (token revoked, refresh-token absolute lifespan exceeded), the session is deleted and the cookie is cleared. Logout (`/auth/logout`) revokes the refresh token at Keycloak, then ends the SSO session, then clears the local session — the chain is documented in T6 of the Threat Model Summary below.

**Production-deployment alternative.** Add explicit idle-timeout tracking — for example, persist a `last_activity_at` column on `sessions`, update it on each authenticated request, and reject sessions with `now - last_activity_at > IDLE_TIMEOUT` (typical values: 15 minutes to 4 hours depending on the threat model). Combine with a tighter absolute timeout (typical: 8 hours to 24 hours) instead of relying on the refresh-token lifespan.

**Authority.** [`_bmad-output/planning-artifacts/architecture.md:1369–1373`](../_bmad-output/planning-artifacts/architecture.md) — "Operational Details" → "Idle / absolute session timeout."

## Threat Model Summary

Seven threats considered. For each: one sentence stating the threat, one short paragraph (2–4 sentences) explaining the mitigation. This is a prose-style threat summary — not a STRIDE / LINDDUN matrix and not an attack-tree diagram. A reviewer can scan this section in under five minutes and know what the system defends against.

### T1 — XSS in the SPA exfiltrates user tokens

A successful cross-site-scripting injection in the SPA gives the attacker arbitrary JavaScript execution in the user's browser; the standard goal is to steal credentials.

The token-isolation contract from §1 (and PRD §8) means a successful XSS attacker recovers **zero token material from the browser**: the session cookie is `HttpOnly`; access / refresh / id tokens never leave the server; the CSRF cookie is readable but is HMAC-bound to a server-side `csrf_secret`, useful only for the current browser-session, and rotated on every login. CSP `script-src 'self'` blocks the most common injection vectors (inline scripts; external script tags) and `connect-src 'self'` prevents exfiltration to attacker-controlled domains. Angular's auto-escaping default closes the template-side injection point. The remaining XSS impact is "the attacker can use the user's browser for as long as the current session cookie is valid" — equivalent to brief unattended-laptop access, not a long-term credential compromise. Mitigation pinned by §1, §6, and the SPA's `bypassSecurityTrust*`-free codebase.

### T2 — CSRF on BFF state-changing endpoints

An attacker hosting a malicious page in another origin gets the user to issue a state-changing request to the BFF, relying on the browser's automatic cookie attachment.

The CSRF middleware in §3 is the load-bearing defense. Three independent layers: the `X-CSRF-Token` header must match the CSRF cookie (which an attacker on another origin cannot read because of the same-origin policy on cookie reads); the `Origin` or `Referer` header must match the BFF's base URL (which the browser sets and the attacker cannot forge); `SameSite=Lax` is a browser-side belt-and-braces that the modern browser landscape provides as a fallback. All three must align for the request to reach the handler; any failure short-circuits to `403 csrf_invalid`. The exempt-method list (GET / HEAD / OPTIONS) is intentionally narrow and the `/v1/test/reset` exemption is gated by an off-by-default env flag.

### T3 — Token replay after stealing the bearer in transit

An attacker intercepts the `Authorization: Bearer <access_token>` header — for example, through a misconfigured intermediate proxy or a TLS-stripping attack — and replays it against the RS.

Mitigations are layered. Keycloak's default access-token lifetime is short (5 minutes; configurable per realm), so a stolen bearer expires fast. The deployment assumes TLS everywhere (`Secure` cookie attribute in production); HSTS would harden this further (Known Gap). The refresh token — the long-lived credential — never crosses the SPA boundary, so a network-level interception of the SPA's traffic cannot capture it. Logout revokes the refresh token at Keycloak, after which any captured refresh token is unusable; the BFF clears the session row even if revocation fails (degrade-honestly per `/auth/logout` flow). Pinned by Story 3.5's `ResourceServerClient` 401-refresh-replay tests and Story 1.13's J5 logout E2E.

### T4 — Direct RS access bypassing the SPA flow

An attacker presents a valid bearer token directly to the RS, skipping the SPA / BFF flow entirely.

This is **intentionally accepted**. The RS is a stateless OAuth resource server: anyone holding a valid bearer JWT with the correct `aud` (`bmad-books-resource-server`) and the required scope can call it. The trust boundary is the JWT validation pipeline (§4) plus the scope enforcement (§5), not "did the request come from the SPA". This is the canonical OAuth contract — `architecture.md:43` ("BFF does not bypass the RS. No local fallback computation when the RS is unavailable.") makes the same point in the inverse direction. Any client that obtains a token through a valid OAuth flow with the appropriate scopes is a legitimate caller; the system has no per-client allowlist on top of scopes. Architectural authority: PRD §8 + architecture line 42.

### T5 — Scope escalation: a `reading-speed:read`-scoped token calls `PUT /v1/reading-speed`

A caller possesses a valid bearer for the RS but only the `reading-speed:read` scope, and attempts a write operation.

The `require_scope("reading-speed:write")` dependency on the PUT handler (§5) rejects the request with `403 forbidden_scope`. The check happens before any handler code runs (FastAPI dependency resolution order). The scope set is sourced from the verified JWT's `scope` claim — an attacker would need to forge a token that survives JWT validation (signature, issuer, audience, expiry) AND carries the missing scope, which collapses to the JWT-forgery threat already covered by §4. Pinned by `services/resource-server/tests/api/test_reading_speed.py::test_put_returns_403_forbidden_scope_when_only_read_scope_present` (line 136) and the symmetric GET case at line 76.

### T6 — Refresh-token replay after logout

The user clicks logout; an attacker who previously captured the refresh token attempts to use it.

The `/auth/logout` flow performs three steps in order: revoke the refresh token at Keycloak's `revocation_endpoint`, call the `end_session_endpoint` to terminate the SSO session, clear the local BFF session row and the session cookie. Even if revocation fails (network error, Keycloak transiently unreachable), the BFF still clears the local session and returns 204 — the user appears logged out from the SPA's perspective, the captured refresh token may still work against Keycloak briefly until revocation eventually succeeds or the token's max-lifespan window closes, but the SPA cannot reach the BFF's session-backed surface because the cookie is gone. The "degrade honestly" contract here is documented in architecture A7 (lines 353–354). Pinned by Story 1.13's J5 E2E spec at [`e2e/tests/j5-logout.spec.ts`](../e2e/tests/j5-logout.spec.ts).

### T7 — Confused-deputy via `sub` injection

The BFF — acting on behalf of user A — sneaks user B's `sub` into a request to the RS; the RS trusts the injected value and operates on user B's data.

Two architectural rules close this attack. First, the BFF's `ResourceServerClient` never injects `sub` into the body, path, or query of any RS call — the compute-estimate path sends only `{"pages": <int>}`; the reading-speed proxies send only the user's payload. Second, the RS reads `sub` only from the verified JWT (see `_principal_from_claims` at `services/resource-server/src/resource_server/auth/oidc_bearer.py:96–112`); no endpoint accepts a body or path identifier for user. The two rules are pinned by Story 4.2's estimate-pass-through tests (`services/bff/tests/services/test_resource_server_client.py::test_compute_estimate_*`) and Story 3.3 / 4.1's RS-side tests. A future bug that adds a `sub` body field on either side would have to fail those tests before it could land.

## Known Gaps / Future Work

Items below are real concerns the project has chosen not to address, captured here so a reviewer can see them and a future operator can act on them. Each cites its defer ID in [`_bmad-output/implementation-artifacts/deferred-work.md`](../_bmad-output/implementation-artifacts/deferred-work.md). Story 5.2 does NOT close any of these; the security review's purpose is to surface them, not to silently bypass them.

1. **CSP hardening directives.** The current CSP lacks `object-src 'none'`, `upgrade-insecure-requests`, and `report-uri` / `report-to`; `style-src 'unsafe-inline'` is permanent; there is no per-request nonce or hash on the script side. Production hardening would (a) compute a per-request nonce for inlined Tailwind styles via a build-time injector, (b) add `object-src 'none'` + `upgrade-insecure-requests` (both are pure additions, no test churn), (c) wire a CSP-report collector. Authority: D371. Severity: medium.

2. **Additional HTTP security headers.** Only CSP is attached today. A hardening pass adds `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security` (TLS-only deployments), `X-Frame-Options: DENY` (legacy fallback for `frame-ancestors`), `Permissions-Policy` (camera/microphone/geolocation deny), and the COOP/CORP/COEP triplet. Authority: D372. Severity: medium.

3. **PyJWT `leeway` is 0 on both BFF and RS.** Clock skew of 1–2 seconds between Keycloak and a backend would cause spurious `ExpiredSignatureError` → `401 session_expired`. Hardening pass: `leeway=timedelta(seconds=10)` on both `jwt.decode` call sites — a single-line change to `_validate_access_token` in `oidc_bearer.py:80–87` and the parallel `jwt.decode` in `keycloak_cookie_session.py:204–246`. Authority: D43 (BFF) + D64 (RS). Severity: medium (real-world likelihood under cold-start clock-drift; mitigated today by NTP-synced hosts).

4. **`WWW-Authenticate: Bearer` header missing on RS 401 responses.** RFC 6750 §3 mandates that an OAuth-protected resource emit `WWW-Authenticate: Bearer ...` on `401 Unauthorized` so the client knows which scheme to retry with. The RS's `AppException` envelope does not add the header today. The BFF's `ResourceServerClient` doesn't inspect it, so no current consumer is broken — this is RFC compliance, not behavioral correctness. Authority: D63. Severity: nit.

5. **Empty `sub` claim surfaces as 412 not 401.** RFC 7519 permits a literal empty-string `sub` (Keycloak does not emit one, but a non-Keycloak IdP could). The RS's `_principal_from_claims` defensively defaults `claims.get("sub", "")`, and the downstream `get_for_user(session, "")` path returns `412 reading_speed_unset` instead of failing authentication. Architecturally an empty `sub` should fail at the auth boundary. Authority: D67. Severity: low (theoretical; no current IdP triggers it).

6. **Refresh-token rotation race under concurrent BFF calls.** Two concurrent BFF requests for the same session that both receive `401 invalid_token` from the RS will both call `_refresh_access_token`; Keycloak's single-use refresh-token rotation accepts the first; the second receives `400 invalid_grant`, which the client maps to session termination — clobbering the freshly-rotated tokens. A user making 2+ concurrent requests around the token-expiry boundary gets logged out. Real production risk under HTTP/2 multiplexing or slow networks. Fix: DB-level `SELECT … FOR UPDATE` with re-read on the `sessions` row — this coordinates correctly across horizontally scaled BFF replicas. A per-process `asyncio.Lock` keyed by `session_id` is sufficient for a single-replica deployment but does not coordinate across replicas (each process has its own lock table), so the DB-level approach is preferred. Authority: D80. Severity: medium.

7. **`httpx.AsyncClient` defaults — `follow_redirects=False` and per-call client.** The BFF's RS / Keycloak callers do not follow redirects; an intermediary that 301s `http://` to `https://` would surface as `_RefreshFailed("malformed_response")` → session deletion. Each call also constructs and tears down a fresh `AsyncClient`, defeating keep-alive. Authority: D83 (`follow_redirects=False`) + D82 (per-call clients; performance-relevant, security-relevant under sustained load). Severity: low (D83) / medium (D82).

8. **Log hygiene — `sub` in cleartext + 8-char session-id prefixes.** The BFF logs `sub` in cleartext on every refresh attempt (PII concern in some jurisdictions). Session-id 8-character prefixes (`session_row.id[:8]`) collide under the birthday paradox at ~thousands of sessions, so incident-correlation across WARN logs becomes lossy. Fix: lengthen prefix to 16 chars (or hash-and-truncate); hash or rate-limit `sub` logging. Authority: D84. Severity: medium.

9. **Bearer / Authorization header parsing — case-sensitivity + multi-bearer concat.** The RS's `_classify_auth_failure` requires the literal `Bearer ` prefix (RFC 6750 §2.1 makes the scheme name case-insensitive); the BFF and RS both fail to detect the RFC 9110 §5.3 multi-header concat case (`Authorization: Bearer real, Bearer evil`). No current consumer trips these — `curl` / `httpx` / Python `requests` all emit `Bearer` literal, and the project's deployment topology has no header-concatenating intermediary — but a future Playwright fixture using `BEARER` or a reverse-proxy that merges duplicate headers would silently fail. Authority: D73 (case) + D74 / D85 (multi-bearer). Severity: nit (RFC compliance).

10. **`bff.api.test_reset.register_test_reset_router` does not reject `TEST_RESET_TOKEN=change-me`.** The RS half (Story 3.4) added a `_PLACEHOLDER_TOKEN` check that refuses to mount the route when the literal `change-me` placeholder reaches the gate. The BFF half does not yet. Defense-in-depth parity: D71. Severity: nit (the route is off by default and the `e2e` profile is operator-opt-in; the `change-me` literal would have to (a) be in `.env` and (b) survive `ENABLE_TEST_RESET=true` gate).

11. **`router` exposed via `__all__` in both test-reset modules.** A future maintainer who mirrors the v1 / v2 routing pattern and writes `from bff.api.test_reset import router; app.include_router(router)` (instead of calling `register_test_reset_router`) silently mounts the endpoint with no env-flag check at registration. The handler still requires the bearer, but on a default-profile build with `TEST_RESET_TOKEN=change-me` the placeholder becomes the auth secret. Fix: rename to `_router` (private), drop from `__all__`, OR construct the `APIRouter` lazily inside the gate helper. Authority: D75. Severity: medium (footgun pattern that depends on a future mistake to materialize).

12. **Non-`AppException` exceptions bypass the project error envelope.** A bare `sqlalchemy.exc.OperationalError` from a driver-level failure propagates as ASGI default `text/plain "Internal Server Error"` — NOT the project's `{"errorCode": "internal_error", ...}` envelope. The RS / BFF both have this gap on every endpoint. Fix: register a catch-all `Exception` handler in `main.py` emitting `ErrorCode.INTERNAL_ERROR`. Authority: D79. Severity: low.

13. **BFF `validation_exception_handler` emits `VALIDATION_ERROR` instead of project-standard `invalid_input`.** The RS was migrated to `invalid_input` (lower_snake) in Story 3.3; the BFF still emits the archetype-default `VALIDATION_ERROR` (upper_snake). Operator-visible wire-code drift. Authority: D81. Severity: medium.

14. **Health endpoint amplification.** `services/bff/src/bff/api/health.py:116–135` does per-request engine setup, parses Alembic config, makes an outbound httpx request to the OIDC discovery endpoint, and has no rate limit. Compose's 30s × 5s × 30 retries window admits roughly five outbound discovery requests per second from a single source. Fix: cache the OIDC discovery probe, or drop it from `/health` and rely on the startup-time check only. Authority: D25. Severity: low.

15. **`BFF_CLIENT_SECRET` shared between the production confidential client and the Playwright runner.** `compose/app.yml:87` plumbs the real `bmad-books-bff` client secret into the e2e Playwright container. Test artifacts (traces, screenshots, videos under `e2e/test-results/`) could capture the credential on a failed run. Clean fix: add a separate `bmad-books-bff-test` confidential client to the realm, used only under the `e2e` profile. Authority: D440. Severity: low.

16. **Log-injection: `_safe_session_id_log` does not sanitize newlines / control characters in `sub`.** A maliciously-shaped JWT `sub` claim (RFC 7519 forbids it; the BFF does not validate the character set) could log-split — e.g., a `sub` containing `\n2026-05-18 12:00:00 ERROR fake_log_line` would forge a fabricated log line. The RS's mirror (`services/resource-server/src/resource_server/api/test_reset.py:106`) shares the gap. Fix: strip non-printable characters in `_safe_session_id_log` before formatting. Authority: D441. Severity: low (no current IdP issues malicious `sub` values, but the validation gap is real).

17. **`session_not_found` envelope shape differs from auth-failure 401 envelope.** A probe that has already passed bearer authentication can distinguish a missing-session 404 from an auth-failure 401 by envelope shape — minor probe side-channel after deeper compromise. Authority: D442. Severity: nit.

18. **Zero-width / BOM characters pass `_strip_and_reject_blank` in book titles.** A book title consisting solely of U+200B (ZWSP), U+FEFF (BOM), or U+2060 (Word Joiner) passes the boundary validator and persists as a visually-empty row. Not a security boundary today (no XSS or injection consequences) but a defensive-input-validation gap that a Unicode-aware adversary could exploit to spoof empty rows. Authority: D470. Severity: low.

19. **No GitHub Actions (or any) CI workflow.** Per architecture I7, the project relies on local test gates run before commit. Production deployments would add a CI workflow that runs lint + tests + Docker build + Playwright across PRs and on `main`. This is out of scope per PRD §4 / architecture I7 — captured here as a Known Gap so the reviewer can see it was a conscious choice, not an oversight.
